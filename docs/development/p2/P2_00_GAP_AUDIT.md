## 3. Concrete contract conflicts and bounded gaps

**G1 — mode is silently ineffective.** `web/src/features/ai-copilot/AuthorMemoryPanel.tsx` setup button sends mode extract. `ai-service/api/schemas.py:IdeaBootstrapRequest` accepts only novel_id/idea/outline/locale/preferences/author_constraints and defaults to Pydantic extra-ignore; `api/narrative_routes.py:bootstrap_from_idea` forwards no mode. `application/bootstrap_service.py:start_from_idea` always generates a blueprint. Add real typed dispatch and fail-closed validation before exposing an extract-ready claim; do not merely rename the response.

**G2 — source and nonhistorical settings are mixed.** Same service passes outline to the model, creates premise/world-rule/constraint facts with empty evidence and entity proposals without explicit-source checking. No-provider fallback creates genre/tone facts and no entities. This does not prove timeline events are already inserted (they are not); it shows extract's explicit-only/non-Canon-settings invariant is not enforced. Persist immutable setup input/hash/mode separately; validate extracted entities only against setup, never hint/outline names. Blueprint output needs model_proposed origin and separate explicit author acceptance, not a fake occurrence. Existing accepted proposal statuses keep their Canon meaning.

**G3 — identity rules do not carry into setup.** Name-hash proposal IDs collide for homonymous candidates, and repository accept falls back to normalized-name resolution when entity_id is absent. Reuse accepted H04/H05 validation and opaque reserved-ID semantics for author-controlled setup identities. Distinct same-name declarations must not be silently merged; unresolved ambiguity blocks setup approval. Do not allocate canonical identity from machine grouping or misuse arbitrary client UUIDs. Setup review scope must use tenant/novel/immutable setup hash/job+review version, not a fabricated chapter/revision. Existing create_author_entity emits source_type author_declaration/Unknown with no occurrence but rejects existing same-name entries; it is a reuse starting point, not a complete homonym solution.

**G4 — activation is weaker than Canon acceptance.** `bootstrap_service.activate_baseline` checks required∩pending outside the repository transaction; it does not validate every required ID exists with an allowed terminal decision, and has no expected Brain version. Repository activate_baseline scopes job/Brain and locks Brain, but does not repeat those checks; service then saves completed job separately. A future repair must scope/lock/revalidate eligible job, complete decisions and expected version, and update active state+job completion atomically under the existing Brain lock. Acceptance/rejection races and failures must not produce active-but-unreviewed baselines. Activation alone currently does not increment Brain version; retain semantics unless owner explicitly changes them.

**G5 — setup activation cannot unlock ordinary first-chapter snapshots.** `bootstrap_service.activate_baseline` chooses None when revisions=(); `postgres_narrative_repository.activate_baseline` persists null; `backend/src/modules/novels/chapter-revisions.service.ts:checkStoryBrainActive` requires a real baseline_revision_id. Normal content PATCH then calls snapshotSavedChapter, which declines the snapshot. `chapters.service.ts:createChapter` stores initial Mongo draft without creating an immutable revision. Distinguish a valid activated setup baseline from absence of baseline without inventing a revision. Use the same snapshot/writer/outbox path for first meaningful create/save, retain pre-baseline no-outbox behavior and manuscript bootstrap restrictions. Historical02A explicitly invokes `/chapters/:id/revisions/snapshot`, so it does not close this autosave gap.

**G6 — setup retry is serialized, not atomic lifecycle replay.** Deterministic job identity includes tenant/novel/locale/idea/outline/preferences/constraints; sequential retry returns existing job. Provider work happens before durable job creation; analysis run, proposal save and job creation use separate repository transactions. Concurrent first requests and failure between proposal save and job creation need real-PG tests and an atomic finalization/reservation design using existing job states and Brain lock. Changed identity fields (mode/setup version/identity decisions) must participate in hashing. Do not hold DB locks through network/provider calls.

**G7 — request tenant is not repository tenant routing.** Gateway's forwardRequest supplies a fixed default tenant unless options overrides it; repository_factory constructs one app-state repository for settings.default_tenant_id. PostgreSQL operations use configured tenant predicates, but narrative setup/plan routes do not reject conflicting X-Tenant-Id as entity_hitl_routes.author_scope does. Enforce configured-scope mismatch rejection in relevant trusted routes (or an approved existing scoped factory); no new multi-tenant architecture is proposed. Public Gateway already enforces auth, active AUTHOR/ADMIN and novel ownership, including plan-by-ID read before response. Preserve inherited ADMIN policy. getStoryPlanController conditionally checks data.novel_id; require malformed upstream records to fail closed. No cross-tenant HTTP exploit is claimed from inspection alone.

**G8 — planning exists, but concurrency and suggestion are limited.** `create_story_plan` has canonical-input idempotency precheck and unique tenant/novel/version, not a unique scoped idempotency key or lock across version allocation. `activate_story_plan` transactionally supersedes prior active plans but has no expected active-plan/version CAS or serialized activation proof. FE create+activate is two requests with no retry key. Smallest hardening: existing scoped Brain lock (or equivalent established lock) around plan key/version/activation decisions; stable client operation key, deterministic replay and explicit plan-version guard. A new schema is not assumed necessary. suggestion stub is optional separate scope; manual optional planning suffices to begin P2 unless owner requires model suggestions.

**G9 — UI surfaces are not one memory.** `/author/context/:novelId` → AuthorStoryContextPage/story-context-api uses Node `/novels/:id/characters`, relationships, timeline and summaries, distinct from approved narrative Canon. Do not treat these records as setup approved memory or synchronize them by matching names. Author IDE's AuthorMemoryPanel uses the approved-memory/review/plan clients. No duplicate memory store or broad legacy refactor is warranted for P2.
