### New finding — P0, cross-author bootstrap resume without novel ownership check

**Source evidence:**
1. `backend/src/modules/ai/ai-gateway.routes.ts` attaches `requireAuth` and AUTHOR/ADMIN role; it exposes `POST /jobs/:jobId/resume`. Authentication is **not equivalent to novel authorization**.
2. `backend/src/modules/ai/ai-gateway.controller.ts:resumeJobController()` (near line 281) obtains `req.auth!.userId` and directly calls `aiGatewayService.forwardRequest({method:'POST',path:'/v1/jobs/'+jobId+'/resume',userId})`, **without fetching the job and calling `assertNovelOwnership`**. By contrast, `getJobStatusController()` immediately above obtains the job first and verifies its returned `novel_id` if present.
3. `ai-service/api/narrative_routes.py:resume_job()` (near lines 626–640) loads the bootstrap job by ID, conditionally schedules `service.resume(job_id)`, and returns status, **without checking the requesting actor against job.novel_id**. AI router uses a service token but its trust boundary allows calls from the backend on behalf of any authenticated author. It cannot substitute for author ownership.
4. `ai-service/application/bootstrap_service.py:resume()` (around lines 445–451) can turn a failed bootstrap job back to queued and execute `process(job.job_id)`; `domain/models.py:BootstrapJob` contains `novel_id` and `tenant_id`. This is a mutable operation, not just a metadata view.

**Security impact / status:** An authenticated unrelated AUTHOR who learns a foreign bootstrap `jobId` can send a resume request across ownership boundaries; the current code path does not deny it. The UUID is an unguessable identifier by design, so exploitation requires knowledge of the job ID, but that is not a permissions control. **This is a source-proven missing guard, NOT a verified live exploit or independently run HTTP negative.** Treat as **P0 targeted acceptance blocker** for integrating all Core endpoints into an author UI.

**Required test:** same tenant, accounts A/B, A creates a scoped bootstrap job (with valid failed/runnable state); B attempts `POST /api/v1/ai/jobs/:jobId/resume` and receives **403**, with no job state/outbox/provider side effects. Test missing job=404, owner A authorized expected behavior, optional admin according to existing ownership policy, and a job with missing/invalid `novel_id` **fail closed**. Compare pre-fix and post-fix runtime evidence on fresh databases only. Authenticated negative 403 must be enforced **before forwarding a mutable resume request**. The related GET `/jobs/:jobId` currently checks ownership only when `data.novel_id` is truthy: evaluate whether a missing scope must fail closed to avoid a fail-open response, with backwards-compatibility tests.
  
**Preferred bounded repair:** at backend controller obtain immutable job metadata through service-token authenticated internal gateway, validate `novel_id` and assert actual novel ownership, only then POST resume; forbid cross-owner and missing scope. Consider AI-side actor/scope enforcement as defence in depth where a trusted actor is available without breaking internal tasks. Do not infer that adding a user-provided `novel_id` query param is authorization. No FE edits.
